# Decisions and Assumptions

The Phase 1 audit left six open decisions (AUDIT.md §13). The owner asked the team to proceed without waiting, so each one below records the assumption that was made, why, and what changes if it turns out to be wrong. Each entry is written so it can be reversed.

| # | Decision | Assumption taken | Reversal cost |
|---|---|---|---|
| D1 | Tenant boundary | **Account = tenant (one business).** Shops are branches inside it. All tenant data carries both `accountId` and `shopId`; isolation between businesses is enforced on `accountId`, and branch visibility on `shopId`. | Medium: moving to per-shop isolation only means tightening the branch rules; the data model already carries `shopId`. |
| D2 | Login identity | **Usernames are unique per business, not globally.** Each business gets a short **business code** (`Account.slug`). Login accepts `username` + optional `business_code`. With no code, a username that exists in exactly one business logs in as before (existing users are unaffected). If it exists in several, the API answers `409 BUSINESS_CODE_REQUIRED` and the clients show the business-code field. Platform admins stay globally unique (they have no business). | Low: adding email login later is additive. |
| D3 | Password reset | **No reset code is ever returned by the API.** Two channels: (1) owners and admins set a new password for their own staff from the Team screen; (2) self-service reset sends a single-use, hashed, 15-minute token by email when the user has an email and SMTP is configured. Without SMTP, production answers with the same generic message and sends nothing (the token is only logged in development). Platform admins recover through the existing `reset:password` CLI script. | Low: SMS delivery can be added as another notifier driver. |
| D4 | Image storage | **Storage abstraction with two drivers:** `local` (default, a directory that must be a persistent volume in production) and `s3` (any S3-compatible service: AWS S3, Cloudflare R2, DigitalOcean Spaces, MinIO). The database stores **keys**, never URLs. URLs are built when a response is sent. Customer photos, ID documents, receipts, and damage photos are **private** (short-lived signed URLs); equipment photos, logos, and QR codes are **public**. Images are re-encoded to WebP with EXIF stripped, plus a thumbnail. | Low: switching the driver is an environment variable. |
| D5 | React Native `mobile-app` | **Treated as retired and replaced by the Flutter app.** The source is not in the workspace, and the Flutter app was built as its replacement. Anonymous API reads are removed, as security requires. Any still-installed RN build keeps working only for logged-in calls. | If RN is still shipped: it must send the bearer token on every list call (it already does after login, per the migration contract docs). |
| D6 | Customer uniqueness | **Phone numbers are unique per shop** (current behaviour kept), compared on a normalized form so `+91 98765 43210` and `9876543210` match. The unique index includes `accountId`, so two businesses can never collide. | Low: widening to per-business is an index change. |

## Other assumptions

- **Photos (added 2026-09-24).** Equipment keeps at most 4 photos, enforced by the API; older items with more keep them until someone removes some. A multi-photo selection is uploaded as parallel single-image requests rather than one batch request, so one bad photo doesn't fail the others and each has its own progress; the form won't save while any photo is uploading or failed. Removing a photo never deletes the file, because duplicated items share keys. Staff users have no profile photo in the data model; their avatars show initials through the same `Avatar` component.

- **Production data is never touched by the team.** Every data migration is a script that defaults to a dry run and must be run by the owner (see [DEPLOYMENT.md](DEPLOYMENT.md)). Nothing was run against the database in `nodejs-backend/.env`.
- **MongoDB transactions** are used for stock, rentals, and payments. MongoDB Atlas supports them. For a local standalone `mongod` (no replica set), the code falls back to non-transactional writes and logs a warning. `docker-compose.yml` starts a single-node replica set, so development matches production.
- **Money** stays a JavaScript `Number` in the database, for compatibility with existing data, but every stored amount is rounded to 2 decimals at the service layer. Moving to integer minor units is recorded as follow-up work.
- **Multi-line rentals** keep one `Rental` document per equipment line, for compatibility with existing data and both clients. Lines created together now share an `orderId`, the advance is split across lines instead of copied, and returns can be processed as one server-side batch. A full `RentalOrder` document model is follow-up work.
- **Rate limiting** uses the in-process store. Deployments with more than one API instance need a shared store (Redis); this is noted in DEPLOYMENT.md.
- **Stripe** stays optional. Plans map to Stripe prices via `Plan.stripePriceId`.
