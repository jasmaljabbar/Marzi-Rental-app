# Field validation and local persistence audit

## Scope and evidence

The mobile app is Flutter (`flutter-app/lib`); the API is Express, Zod and Mongoose (`nodejs-backend/src`). Existing uncommitted UI work was retained. Before this change, the mobile repository directly called HTTP for every read and write. Preferences stored the session presentation settings; there was no durable business-record cache or synchronization queue. The attachment refers to an earlier architecture request that was not present in this session. This implementation therefore adds a bounded local-first path, not offline stock allocation or payment settlement.

## Field audit

| Area | Evidence and resulting rule |
| --- | --- |
| Authentication / profile / team | Existing username syntax (64 characters for new usernames), 200-character login identifiers, password policy and roles remain authoritative. Required login inputs and registration fields now validate inline. Optional emails are trimmed, lowercased on submission, and structurally validated. Passwords are never trimmed. |
| Customers | Name is required, at most 120 characters; phone is required; address is optional, at most 500. Customer and company forms share a country selector and phone field. Changed/new phones are validated against country metadata. |
| Company / shops | Optional phones and emails validate when supplied. Existing schema limits for address, tax ID, footer and company/shop names are retained. Tax percentages remain decimal values between 0 and 100. No invented tax-ID format is enforced. |
| Equipment | Category and name are required. Initial stock is a non-negative whole number, at most 1,000,000. Damaged stock cannot exceed initial stock. Price, deposit and daily rate are decimal money values. Useful life remains numeric from 0 to 100; zero is no longer silently replaced by five. |
| Stock / scrap / maintenance / reservations / sales | Quantity is a positive whole number, at most 100,000. Current stock, tenant ownership, reservation conflicts and archive rules are checked by existing transactional services. Decimal or signed count input is not silently changed into a different positive integer. |
| Rentals | Required selections and quantity limits validate before HTTP. Expected return dates cannot precede the rental calendar date, including edits. Actual start/return timestamps are generated by the server, not entered by users. Existing advance-versus-estimate checks remain in place. |
| Returns / payments | Money remains decimal, finite, non-negative, at most 10 billion, with at most two decimal places. Damaged quantities cannot exceed rented quantities. Existing discount-cap, refund and payment-allocation policies remain intact; they are explicit settlement rules, not generic numeric coercion. |
| Expenses / recurring expenses | Expense category is required (80 characters); amount may be zero per the existing API/model. Payment modes remain enumerated. Recurring day must be an integer from 1 to 28. Real calendar dates are required. |
| Categories | Required trimmed name, 80 characters; existing icon enumeration and case-insensitive uniqueness remain. |
| Search / filters / reports | Existing bounded search strings and IDs remain server-validated. Both local API calls and backend list/report schemas reject reversed date ranges. Search punctuation is escaped by existing server search helpers; it is not treated as a regex. |
| Settings / platform | Invalid discount percentages and fractional/negative stock thresholds are rejected instead of silently clamped or rounded. Platform numeric inputs no longer coerce booleans or empty strings to numbers. Plan date ranges are ordered. |
| IDs / generated codes | ObjectId, username, setting-key and plan-key rules are reused. Invoice/rental identifiers remain server-generated. Drafts cannot use unsynchronized category/equipment identifiers. |
| Images / files | Existing upload type checks, decoded-image validation, tenant ownership checks and 10 MB default limit remain. Mobile additionally rejects empty files and duplicate bytes within the current selection session. Multi-select, four-equipment-photo limit, legacy extra-photo preservation and failed-upload retry remain. Existing remote photos are not downloaded to detect byte duplicates. |

The reusable mobile `Field` and `ActionButton` validate within forms. Upload actions can operate before the rest of a form is complete. Errors appear after interaction or submission and preserve entered values. Strict input parsing is separate from tolerant display parsing. The repository validates catalog payloads again before persistence. Zod remains the API security boundary, with service checks for database-dependent constraints.

## Phone storage and compatibility

The database previously stored display text in `phone`, with a punctuation-stripped comparison value in `phoneNormalized`; local Indian and `+91` forms could differ. New and changed values use E.164 in both fields. The mobile field separates selected country from local entry and adds the calling code exactly once. Local Indian input must have exactly ten digits; other countries use maintained metadata, including legitimate shorter national numbers. The generic phone fields continue to accept valid fixed lines as well as mobiles.

Backend validation uses [`libphonenumber-js/max`](https://github.com/catamphetamine/libphonenumber-js); Flutter uses [`phone_numbers_parser`](https://pub.dev/packages/phone_numbers_parser). Metadata versions can differ, so the server remains authoritative and rejected drafts remain correctable. Legacy clients without a country selector retain the documented Indian default for national-format input. International clients must send a leading `+` and calling code.

No production database was connected to, rewritten, or migrated. Reads preserve old values. Lookup and duplicate detection check canonical and legacy Indian keys. Exact unchanged invalid legacy phone values may remain during unrelated edits; a changed phone must validate. This exception is scoped to the authenticated existing record and cannot create a new invalid phone.

If a bulk normalization is later desired: take a backup, export scoped IDs and phone keys, produce a dry-run report, separate ambiguous national numbers from known international/Indian numbers, resolve same-shop collisions manually, then update in bounded batches with original values recorded for rollback. Do not infer a foreign country from digits alone. Recheck the unique index and canonical/legacy lookups before enabling any backfill. The existing migration scripts are not run by this change.

## Local-first behavior and boundaries

[Sembast](https://pub.dev/packages/sembast) stores records durably in the application support directory on native platforms and IndexedDB on web. Cache and queue keys include server URL, authenticated user ID and active shop ID. The token remains in secure storage. Cached reads return immediately; stale entries refresh in the background after 30 seconds, with concurrent identical fetches shared. Cache invalidation marks entries stale so a connection loss does not erase the last usable data. Startup no longer blocks on a health request.

New customers, categories, equipment and expenses are validated and durably saved as pending before HTTP. The app retries after saving, at startup, every 30 seconds while running, and from **Pending changes**. A global badge and More menu expose pending records. Pending customer/category IDs are not offered as confirmed rental dependencies. These drafts are visible in Pending changes until authoritative server records are available.

Each queued create has a stable UUID. The API validates it, stores it in the existing unique `syncId`, and records a hash of the validated payload. Identical retries return the original record; a changed payload with an already committed ID returns a conflict. Equipment stock/purchase side effects remain inside the existing transaction. Replays are scoped to the authenticated shop and checked before plan counts. A simultaneous duplicate may initially return conflict; retrying the same payload resolves to the existing record without creating another.

Definitive validation/business rejections become **Needs attention**, preserve all payload data, and expose **Correct and retry**. Connection errors, server errors, timeouts, authentication failures and ambiguous replay conflicts remain pending. Uncertain operations are not editable until their result is resolved, avoiding duplicate writes after a lost response. Nothing silently deletes a rejected draft. Logout hides drafts from other users; signing back into the same user and shop restores access.

Edits, stock movements, reservations, rentals, returns, payments, deletes and file uploads still require the server. Their UI keeps entered data on failure, but they are not persisted as offline transactions. This avoids inventing conflict resolution for concurrent stock, stale edits or duplicate payments. Uploaded files must finish before saving a draft that references them. Local storage does not provide protection against device compromise or browser storage eviction. A destructive local-data reset is not implemented.

## Verification

Regression coverage includes India 9/10/11 digits; international numbers with different lengths; duplicate calling codes; letters; malformed emails; empty required text; fractional counts; booleans/empty values/NaN/infinity; money precision; impossible and reversed dates; direct API bypasses; legacy phone reads/edits; replayed creates; equipment side-effect deduplication; durable draft restart; user isolation; offline cached reads; validation rejection, correction and retry; and image duplicate selection. Existing backend and Flutter suites cover stock transactions, tenant isolation, media failures, payments, and responsive layouts.

Deployment order: release the backend validation/replay contract before the new mobile build. Keep the existing unique `syncId` indexes. Old mobile builds can read E.164 phones; invalid new phone submissions must be corrected. Native-device and browser storage-eviction behavior still require deployment-environment smoke testing.

Validation run: backend syntax checks and 112 tests passed; Flutter analysis and 77 tests passed; release web compilation passed. Focused tests also passed after final helper cleanup. Native device smoke testing was not performed.
